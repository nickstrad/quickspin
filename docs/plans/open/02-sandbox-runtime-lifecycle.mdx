# 02 — Sandbox runtime: lifecycle

Depends on: 01.

## Summary

Build the first real Go package: `internal/runtime`, which owns the create → inspect →
destroy lifecycle of a single sandbox backed by a Docker container. Exercise it through
a `quickspin sandbox` CLI subcommand, not HTTP. Everything later (exec, files, the
control plane, other backends) hangs off the interface defined here.

<KeyPoint label="Why this plan matters">
  This is the spine interface of the whole project. Every later plan either calls it
  (control plane, CLI, SDKs) or re-implements it (Firecracker). Getting the contract
  right here is worth more than getting the Docker code pretty.
</KeyPoint>

## Industry context

Every platform has this layer. In E2B it's the code behind `Sandbox.create()`; in
Daytona, the workspace provisioner; in Kubernetes, the kubelet's container-runtime
calls. The industry pattern worth copying is the **backend-neutral interface**: the
caller speaks in sandbox specs and sandbox IDs, never in Docker terms. That is what
lets plan 14 slide Firecracker underneath without rewriting the control plane — exactly
how Daytona supports multiple providers and how Kubernetes swapped Docker for
containerd behind the CRI.

<Compare>
  <CompareItem eyebrow="What you build" title="Interface first, Docker behind it">
    Callers hold a `Runtime` value and quickspin IDs. Docker types never appear in a
    signature, so swapping the backend is a new file, not a refactor.
  </CompareItem>
  <CompareItem eyebrow="The anti-pattern" title="Docker types in the API">
    If `container.ID` or `types.ContainerJSON` leaks into a caller, every future
    backend must fake Docker's shapes. Kubernetes paid years of migration cost for
    exactly this coupling before the CRI existed.
  </CompareItem>
</Compare>

## What you'll learn

- The Docker Engine API from Go (`github.com/moby/moby/client`) — what `docker run`

- Designing a Go interface for a resource lifecycle: constructors, contexts everywhere,
  error taxonomy with `errors.Is`.
- Idempotency as a design property, not an afterthought.
- Labels as the mechanism for "which containers are mine?" — the seed of reconciliation.
- The repo's error and logging conventions applied for the first time (see

### Concept: `docker run` is two calls, and the gap between them is yours

The Docker CLI hides that `run` is `ContainerCreate` (allocate the container, write
its config) followed by `ContainerStart` (actually start the process). Your `Create`
must make both calls — which means it can fail *between* them, leaving a created but
never-started container on the daemon. That half-state is invisible to a caller who
only got back an error. Whoever owns the gap owns the cleanup: `Create` must delete
what it made before returning the error, or every failed create leaks a container.

### Concept: two identities, one owner each

A sandbox has two IDs the moment it exists: the quickspin ID you generate
(`sbx_a1b2c3`) and the container ID Docker generates. They have different owners and
different lifetimes. The quickspin ID is the *durable, public* identity — it will later
live in a database row and appear in URLs. The container ID is a *backend detail* that
changes if the sandbox is ever recreated on another backend or another host. The label
`quickspin.id=sbx_...` is the join between the two worlds, written at create time so
the mapping survives even if your process crashes: any future process can list
containers by label and rediscover what it owns. That rediscovery is the seed of plan
06's reconciler.

<StudyPrompt question="Why not just use the container ID as the sandbox ID?">
  Ask what happens in plan 14 when the same sandbox is backed by a Firecracker microVM
  — there is no container ID. Any identity minted by the backend ties every caller to
  that backend. Identity that must outlive a backend has to be minted above it, which
  is why quickspin generates its own IDs and demotes the container ID to a label-joined
  implementation detail that appears only in logs.
</StudyPrompt>

### Concept: sentinel errors as the public contract

Callers of this package will branch on *kinds* of failure — "not found" gets a 404
later, "image missing" gets a 400 — but they should never parse error strings or
depend on `RuntimeError`'s fields. Go's convention is sentinel values tested with
`errors.Is`, which walks the chain of wrapped errors. Your `RuntimeError` struct rides
along as the diagnostic envelope (operation, message, stack) while the sentinel inside
it remains the only thing callers may rely on.

## Design and interfaces

You implement this interface; it is the spine of the whole project:

```go
package runtime

// Spec describes what to create. Fields expand in later plans.
type Spec struct {
    Image string
    Env   map[string]string
}

type State string

const (
    StateRunning State = "running"
    StateStopped State = "stopped"
)

type Info struct {
    ID        string // quickspin's ID, not the container ID
    State     State
    CreatedAt time.Time
}

// Sentinel errors; callers test with errors.Is.
var (
    ErrNotFound     = errors.New("sandbox not found")
    ErrImageMissing = errors.New("image not available")
)

type Runtime interface {
    Create(ctx context.Context, spec Spec) (Info, error)
    Inspect(ctx context.Context, id string) (Info, error)
    List(ctx context.Context) ([]Info, error)
    // Destroy of an unknown id returns nil: cleanup must be retry-safe.
    Destroy(ctx context.Context, id string) error
}
```

<Callout tone="system" title="Idempotent destroy is a design commitment">
  `Destroy` of an unknown ID returns nil, not `ErrNotFound`. Cleanup code runs in
  retry loops, signal handlers, and reconcilers — if a second destroy fails, every
  caller must special-case "already gone", and some will get it wrong. Deleting an
  absent thing has succeeded.
</Callout>

Decisions the plan commits to:

- Quickspin generates its own sandbox IDs (e.g. `sbx_` + random suffix) and stores them
  on containers as labels (`quickspin.id=...`, `quickspin.managed=true`). Container IDs
  never escape the package (log them for correlation; never join on them).
- Per the error-handling reference: `internal/runtime/errors.go` defines `RuntimeError`
  (`Op`, `Message`, `Err`, `Stack`) with `E`/`Wrap` constructors. Sentinels ride in
  `Err` so `errors.Is(err, ErrNotFound)` works through the chain; the sentinels remain
  the public contract, the struct is the diagnostic envelope.
- Per the code-structure reference: ID generation/validation and the managed-label
  filter are pure helpers (no receiver, no I/O) with their own table-driven tests —
  they are the first entries in what will become each package's decision layer.
- `NewDockerRuntime(client, logger)` takes a `*slog.Logger`; no package-level logging.
- Containers run a long-lived no-op entrypoint (e.g. `sleep infinity`); commands come
  later (plan 03).
- CLI surface: `quickspin sandbox create|list|inspect|destroy`.

## The pure helper layer

The inventory behind the "Write the pure helpers first" task. Ten symbols, in three
families, none of which touch Docker, the clock, or a logger — so all of them are
testable before the daemon is involved at all.

### Identity

| Symbol | Shape | What it owns |
| --- | --- | --- |
| `SandboxIDPrefix` | `const` | The one place `sbx_` is spelled. Nothing else concatenates it by hand. |
| `newSandboxID` | `() string` | Mints prefix + random suffix. The only function that decides what an ID *looks like*. |
| `validateSandboxID` | `(string) error` | Answers "could this string have come from `newSandboxID`?" |

Validation earns its place for one reason: it separates "you gave me nonsense" from "that
sandbox does not exist". Without it, `Inspect("")` builds the filter
`label=quickspin.id=`, matches nothing, and returns `ErrNotFound` — so a typo and a
deleted sandbox produce the same answer, and plan 05 turns both into a `404` that tells a
client debugging a malformed ID exactly the wrong thing. With it, the caller gets
`ErrInvalidSandboxID` before the daemon is ever contacted.

That is the whole benefit, and it is worth sizing honestly before adding rules: rejecting
a bad ID prevents a failed lookup, not a dangerous one.

#### The ID format, exactly

The generated form is the prefix plus a canonical lowercase UUIDv4 — 40 characters total:

```
sbx_9f8e7d6c-5b4a-4938-8271-60514f3e2d1c
^^^^|8------|4---|4---|4---|12----------
     8-4-4-4-12 hex groups, lowercase, hyphen-separated
         ^ version nibble: 4     ^ variant nibble: 8, 9, a, or b
```

A validator built on `uuid.Parse` alone is **weaker than that format**, because
`uuid.Parse` is a permissive reader, not a format checker. What it accepts:

| Input | `uuid.Parse` | Can `newSandboxID` produce it? |
| --- | --- | --- |
| `9f8e7d6c-5b4a-4938-8271-60514f3e2d1c` | accepts | yes — the only true form |
| `9F8E7D6C-5B4A-…` uppercase or mixed | accepts | no — hex decodes case-insensitively |
| `9f8e7d6c5b4a4938827160514f3e2d1c` (32, no hyphens) | accepts | no |
| `{9f8e7d6c-…}` (38, braced) | accepts | no |
| `urn:uuid:9f8e7d6c-…` (45) | accepts | no — and the scheme is case-insensitive too |
| `00000000-0000-0000-0000-000000000000` | accepts | no — the nil UUID, and `uuid.UUID`'s zero value |
| `9f8e7d6c-5b4a-1938-…` version nibble 1, 0, or f | accepts | no — **version is never checked** |
| `9f8e7d6c-5b4a-4938-0271-…` variant nibble 0 | accepts | no — **variant is never checked** |

And what it already rejects, so these need no extra code:

| Input | Why it fails |
| --- | --- |
| `9f8e7d6c_5b4a_…` underscores for hyphens | separator must be `-` |
| `9f8e7d6-c5b4a-…` hyphens in the wrong positions | group widths are fixed |
| 35 or 37 characters | length is exact per accepted form |
| leading space, trailing newline | not trimmed — whitespace is a parse failure |
| `9f8e7d6g-…` non-hex character | `g` is not hex |
| `{9f8e7d6c5b4a…}` braced *and* dashless | the braced form still requires hyphens |

None of this is a safety boundary, and it is worth being precise about why, because the
opposite is easy to assume. Docker's label filters match a value **exactly**, not by
prefix, so a truncated or empty ID under-matches rather than over-matches — it finds
nothing. And `filters.Args` is a structured map serialized to JSON, not a string the ID
is concatenated into, so a `,` or `=` in a value is just a byte in that value with no
delimiter to escape from. What is left is a *correctness* gap: these forms let in IDs
that no `Create` ever minted, and an `Inspect` on one is guaranteed to find nothing.

Every encoding row above closes with one line — re-format the parsed value and compare it
back to the input:

```go
v, err := uuid.Parse(uid)
if err != nil {
    return ErrInvalidSandboxID
}
if v.String() != uid {          // canonical round trip
    return ErrInvalidSandboxID
}
```

`String()` always emits the canonical lowercase 8-4-4-4-12 form, so anything that arrived
in another encoding fails to match. That is one comparison instead of a length check plus
a case check plus a form check, and it cannot drift out of step with the generator,
because the rule is defined by the formatter both sides use rather than by hand-written
constants that have to agree with it.

The nil UUID gets its own check, because it is not the same kind of input as the rest:

```go
if v == uuid.Nil {
    return ErrInvalidSandboxID
}
```

`uuid.UUID` is a `[16]byte`, so this is an array comparison with no allocation — cheaper
than formatting the value to compare against a zeros literal.

<Callout tone="idea" title="Two categories of rejected ID, and where to stop">
  A v1 UUID or a braced encoding can only arrive from **outside** — someone pasted an ID
  from another system. Rejecting those buys a `400 invalid id` instead of a `404 not
  found`, which is the one thing validation genuinely earns: a client debugging a typo can
  act on the first and is misled by the second.

  The nil UUID arrives from **inside**. It is `uuid.UUID`'s zero value, so it is what an
  unassigned struct field, a decode that skipped a key, or a discarded error produces —
  never something a caller types. Catching it turns a whole class of internal bug into an
  immediate error instead of a daemon round trip that reports a sandbox nobody named does
  not exist. It is also the only rule here that survives any future ID format change,
  since all-zeros is never a legitimate value.

  That asymmetry is where to stop. Version and variant checks are left out: they only
  catch outside input, the payoff is one avoided lookup, and each is something to migrate
  if the format ever moves — a `Version() == 4` check would reject UUIDv7 the day you
  decide time-ordered IDs are worth having.
</Callout>

### Labels

| Symbol | Shape | What it owns |
| --- | --- | --- |
| `labelSandboxID`, `labelManaged` | `const` | The two label keys, spelled once. |
| `managedLabels` | `(id string) map[string]string` | The labels written into `container.Config` at create time. |
| `isManaged` | `(labels map[string]string) bool` | "Is this container one of mine?" |
| `sandboxIDFromLabels` | `(labels map[string]string) (string, error)` | The inverse of `managedLabels`: recovers the sandbox ID off a container. |

Two directions plus a predicate — write, read, and test. Round-tripping `managedLabels`
into `sandboxIDFromLabels` pins the key name in both places with one assertion, which is
the failure you actually get: renaming the key in the writer only, leaving every
container unreadable to its own reader.

<Callout tone="warning" title="A missing label at create time is permanent">
  Labels go into `ContainerCreate` and cannot be added afterward. If `managedLabels`
  omits `quickspin.managed`, every container it creates is invisible to `List` for the
  rest of its life — and invisible to the leak check that is supposed to catch exactly
  this. Assert both keys, not just the one you were thinking about.
</Callout>

### Translation

| Symbol | Shape | What it owns |
| --- | --- | --- |
| `stateFromContainerState` | `(string) State` | Collapses Docker's seven container states into this package's two. |
| `envToArgs` | `(map[string]string) []string` | Turns `Spec.Env` into Docker's `KEY=VALUE` slice, in sorted order. |

Neither is named in the task, but both are decisions by the code-structure reference's
own criteria, and both otherwise end up buried in a `docker.go` method where nothing can
reach them. Docker reports `created`, `running`, `paused`, `restarting`, `exited`,
`removing`, and `dead`; you expose two states. Whether `paused` counts as running is a
judgment with consequences, and inside an `if s == "running"` it is an invisible one.

`envToArgs` sorts for a specific reason: Go randomizes map iteration order, so without
sorting the output differs run to run and there is nothing stable to assert against.

<StudyPrompt question="Should the label helpers return Docker's filters.Args, or plain Go values?">
  `ContainerList` wants `filters.Args`, so returning it saves a conversion. But
  `filters` is a moby type, and a pure layer that returns one means the daemon-free test
  binary links the Docker SDK — the coupling this plan's opening section argues against.
  The alternative keeps the helpers in label key/value pairs and lets `docker.go` do the
  one-line translation at the boundary, where it is obvious and unreviewed. These
  helpers are unexported either way, so nothing leaks to callers; the question is only
  what the fast test suite has to link against.
</StudyPrompt>

### `newSandboxID` is the one that is not pure

It reads a random source, so it has no fixed input/output pairs and a table has nothing
to tabulate. That is why its two tests in Definition of done are *property* assertions —
call it a thousand times; every result non-empty, correctly prefixed, all distinct —
rather than rows. The table belongs to `validateSandboxID`, and the pairing is the point:
generate-then-validate in a loop asserts the two agree about the suffix alphabet. A
generator and a validator that disagree means every `Create` mints an ID its own
`Inspect` rejects.

Two choices worth making deliberately rather than inheriting. `uuid.New` panics if the
random source fails where `uuid.NewRandom` returns an error — the panic is defensible (a
broken CSPRNG is not recoverable) but it decides whether `newSandboxID` returns an error,
which decides whether every `Create` carries an extra error branch. And a full UUID
suffix is 36 characters, so IDs read as `sbx_9f8e7d6c-…`; truncating buys readable CLI
output and log lines at the cost of collision headroom that, at one host and one
developer, you have in vast surplus.

### Three decisions the tests have to commit to

- **Does `isManaged` require the ID label, or just the managed marker?** Requiring both
  means a half-labelled container is invisible to `List` — and to `TestNoLeakedContainers`,
  so the bug that writes one label and not the other leaks containers the leak check
  cannot see. Deciding ownership on the marker alone is louder: the container is ours,
  and `sandboxIDFromLabels` is what rejects the bad ID.
- **Are `paused` and `restarting` running or stopped?** Pick, and put each on its own
  table row so the answer is written down rather than implied.
- **Does `validateSandboxID` constrain length, or only the alphabet?** Alphabet-only
  accepts both a full UUID and a truncated suffix, which leaves the truncation decision
  above open. Pinning a length closes it.

  <Hint
    title="Diagnosing the likely failure: leaked containers after test runs"
    check="After a full make test-docker run — including a run where you force a failure — docker ps -a --filter label=quickspin.managed=true prints nothing."
  >
    If `TestNoLeakedContainers` fails intermittently, the leak is almost always one of:
    a `t.Cleanup` registered *after* the create call that failed (register it before,
    keyed on the ID you generated), the create-start gap cleanup missing, or a test
    asserting mid-test state and returning early. Reproduce by making `ContainerStart`
    fail deliberately and watching whether the created container survives. `docker ps
    -a` (with `-a`) is the honest view — created-but-not-started containers do not
    appear without it.
  </Hint>
</HintSteps>

## Definition of done

Pure-helper unit tests (`make test`), table-driven per the code-structure reference:

- `TestNewSandboxIDHasPrefixAndIsUnique` / `TestNewSandboxIDIsNeverEmpty`.
- `TestManagedLabelFilterMatchesOnlyOurs`.
- `TestRuntimeErrorPreservesSentinel` — `errors.Is` finds `ErrNotFound` through an
  `E` + `Wrap` chain (pins the convention itself).

TDD against the real daemon (an integration test here is worth more than a mocked
client). Required tests, all passing via `make test-docker`:

- `TestCreateThenInspect` — create returns a `sbx_` ID; inspect reports running.
- `TestCreateWithMissingImage` — unknown image yields `ErrImageMissing`, and no
  half-created container is left behind (verify by listing labeled containers).
- `TestDestroyIsIdempotent` — destroy twice; second call returns nil.
- `TestInspectUnknownID` — returns `ErrNotFound`.
- `TestListOnlySeesManagedContainers` — a manually-run unlabeled container is invisible.
- Every test cleans up in `t.Cleanup`; a final `TestNoLeakedContainers` (or a shared
  check) asserts zero `quickspin.managed` containers remain.

Deliberately untested: concurrent creates, daemon restarts mid-create, non-Docker
backends.

## Solo-developer tradeoffs

Commercial platforms start at containerd or a microVM for isolation and density; Docker
is a fat dependency with a root daemon. You start with Docker because its API is the
best-documented on-ramp and the interface above quarantines the choice. Also deferred:
image distribution (you pull public images by hand), and any notion of pools or reuse —
one create equals one cold container, measured honestly, until plan 11.
