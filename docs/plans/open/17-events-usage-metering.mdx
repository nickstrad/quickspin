# 17 — Event enrichment and usage metering

Depends on: 11 (tenants on every record); 13 recommended first (the `actor` field and
host attribution earn their place once placement exists). 07's `generation` column
assumed.

## Summary

Make the event log carry its full story, then build the pipeline that turns it into
measured quantities. Part one enriches the `events` table roadmap 06 created:
structured reason codes, an `actor` column (api, reconciler, reaper, scheduler,
admin), `tenant_id`, and the roadmap 07 `generation` — plus API and CLI surfaces for
reading a sandbox's lifecycle history. Part two builds `internal/usage`: a usage
processor that consumes lifecycle events through a checkpointed cursor and derives
usage records (runtime seconds from Running→terminal intervals, billable API
operations), exposed per tenant over the API and CLI. The roadmap ends at
`usage_records`; rollups, pricing, and invoices are recorded as the sequel below. The
controller never computes a quantity — it emits facts; everything downstream is
derived, deletable, and rebuildable from the events.

## Industry context

Metering is a core control-plane responsibility alongside reconciliation, scheduling,
and runtime management: AWS bills from usage records aggregated into the Cost and
Usage Report, Modal and E2B meter per-second sandbox runtime, Stripe built an entire
product line on ingesting usage events and applying pricing after the fact. The
universal shape is the bottom of the one this roadmap builds: immutable facts at the
bottom and a processor deriving normalized usage — with a pricing layer and
aggregation tables above it, which this roadmap stops short of. Nobody serious
computes usage from live runtime state — state says what is true now; metering needs
what was true across time, which only the event history knows.

<KeyPoint label="Facts flow down, quantities are derived">
  events → usage processor → usage_records. Every arrow is re-runnable: delete
  everything downstream of `events` and the pipeline rebuilds it identically. That
  property — derivability — is the test of whether the controller stayed a
  fact-emitter and the usage service stayed a pure consumer, and it is testable at
  the `usage_records` boundary without any pricing above it.
</KeyPoint>

## Key concepts

- Deriving intervals from event pairs: a sandbox's billable runtime is the sum of
  Running→(Stopped|Failed|Destroyed) spans, with the two hard edges — a sandbox still
  running at query time (open interval, meter to `now`) and a sandbox that crashed
  (the terminal event's timestamp truncates the span honestly).
- A checkpointed consumer: the processor remembers the last event ID it processed and
  resumes from there — the smallest form of the cursor/offset pattern every stream
  system (Kafka consumer groups, Postgres logical replication) is built on.
- Idempotent derivation: reprocessing the same events must not double-bill. At-least-
  once delivery plus idempotent writes (unique keys on derived records) is the
  standard alternative to chasing exactly-once.
- Facts versus derived state, again: roadmap 06 taught events-versus-row; this roadmap
  adds the second derivation layer and the discipline that derived tables are caches,
  never sources.

### Concept: billable time is an interval query over an append-only log

The events table stores points in time; billing needs durations. The derivation walks
a sandbox's ordered events and pairs each transition into `running` with the next
terminal transition, summing the gaps. Three cases keep this honest. A sandbox
currently running has an open interval — meter it up to the processing timestamp, and
emit the partial usage record with a marker so the next processor run extends rather
than duplicates it. A sandbox whose host died (roadmap 13) has a `failed` event
written by the reconciler — the customer's meter stops at that event's timestamp, not
at whenever the plane noticed; the event log is precisely what makes that fair. And
ordering comes from the roadmap 07 generation, not from timestamps: two events in the
same clock second still have a total order, which is why the generation column was
worth adding before the billing code that needs it.

### Concept: the processor is a reconciler that never destroys anything

The usage processor has the same shape as roadmap 06's reconciler — a loop that reads
state, decides, writes — but consumes an append-only log instead of converging live
resources. Its correctness rule is idempotence: it may crash after writing usage
records but before advancing its checkpoint, so the same events will be processed
twice, and the write path must tolerate that. The mechanical answer is deterministic
record identity — a usage record's unique key derives from what it measures (sandbox,
interval start generation, metric), so the second processing attempt upserts the same
row instead of inserting a sibling. `TestUsageProcessorIsIdempotent` reprocesses the
whole log from generation zero and asserts totals do not change; if that test needs
special-case code to pass, the record keys are wrong.

## Design and interfaces

```text
events additions (roadmap 06 schema +):
  actor      TEXT NOT NULL      -- api | reconciler | reaper | scheduler | admin
  reason     TEXT NOT NULL      -- structured code: user_requested, ttl_expired,
                                --   readiness_timeout, host_dead, quota_denied, ...
  tenant_id  TEXT NOT NULL      -- denormalized at write time; events are self-contained
  generation INTEGER NOT NULL   -- exists since roadmap 07

usage schema (new, internal/usage owns it):
  usage_records(id, tenant_id, sandbox_id, metric{runtime_seconds, sandbox_create,
                exec_call, file_upload, file_download}, quantity, period_start,
                period_end, source_generation, UNIQUE(sandbox_id, metric,
                source_generation))
  usage_checkpoints(consumer, last_event_id)

API / CLI:
  GET /v1/sandboxes/{id}/events           now returns actor, reason, generation
  GET /v1/usage?from=&to=                 tenant-scoped usage records, summed by metric
  quickspin events <sandbox>              lifecycle history, human-readable
  quickspin admin usage show --tenant --month
```

Committed decisions:

- Lifecycle events are the usage boundary — no separate `UsageStarted`/`UsageStopped`
  events, no periodic metering ticks. Both alternatives are recorded below as the
  paths commercial platforms take at scale; at this scale they duplicate facts the
  log already holds.
- The processor is a loop inside the existing plane binary (same process as the
  reconciler, own ticker, own checkpoint row) — a separate usage *service* is the
  stated future shape once operation volume justifies it, and the package boundary
  (`internal/usage` touching only its own tables plus read-only events) is drawn so
  extraction is mechanical.
- Billable API operations (create, exec, upload, download) are metered from events,
  which means those operations must emit events where they do not yet — the audit
  that closes that gap is part one's real work, not a side effect.
- The pipeline stops at `usage_records`: no rollup tables, no price list, no invoice
  document. With one tenant, aggregation is a query-shape optimization for volume that
  does not exist and pricing is a rate nobody charges — both are recorded as the sequel
  below, and the derivability test that justifies the architecture already runs at this
  boundary.
- Quantities are integers end to end; floats never touch a quantity, and the
  runtime-seconds rounding rule (round up to the next second, like every cloud) is a
  documented, tested decision made here rather than deferred to whatever prices it
  later.

<Callout tone="warning" title="Do not meter from the sandboxes table">
  The row knows what is true now; it has already forgotten the three restarts this
  month. Every quantity in this roadmap derives from events — if a needed fact is not
  in the log, the fix is emitting the missing event, never reading live state from
  the usage path.
</Callout>

### Client surfaces

**CLI.** Add `quickspin events <sandbox>` and `quickspin admin usage show --tenant
--month`; event rows must include actor, reason, and generation, and the usage command
must present the recorded metric quantities without inventing prices or invoices.

**Web app.** Extend the sandbox detail view with a lifecycle timeline showing actor,
reason, and generation, and add the authenticated tenant's usage view with a from/to
filter and totals grouped by metric. It must present immutable usage records, not infer
runtime from the sandbox's current state or display billing amounts this roadmap does
not own.

## Hint steps

<HintSteps>
  <Hint
    title="Start with the emission audit, not the schema"
    check="A grep-driven table in your notes lists every billable operation and the event it emits; the gaps are explicit before any migration is written."
  >
    Walk each public handler and ask "what fact does this leave in the log?" Exec and
    the file endpoints likely emit nothing today — they were workload ops, not state
    transitions. Decide the event shape for operation events (from_state = to_state,
    reason carries the operation) or add an operations-style event kind; either
    works, but pick before the migration so the schema is written once.
  </Hint>
  <Hint
    title="Derive intervals with a pure function over ordered events"
    check="TestRuntimeSecondsFromEvents passes its table: clean stop, crash truncation, still-running open interval, and a stop-start-stop restart pattern each produce the expected seconds."
  >
    `runtimeSeconds(events []Event, now time.Time) []Span` — no store, no clock
    reads inside. Order by generation, not timestamp. The open-interval case returns
    a span ending at `now` with an open marker; the caller (the processor) is what
    turns open spans into extendable records. Table-test this to death before wiring
    the processor — every billing bug you cannot have later is one this table
    catches now.
  </Hint>
  <Hint
    title="Checkpoint after the derived writes, in the same transaction"
    check="TestUsageProcessorIsIdempotent passes: kill the processor between any two operations, rerun from the stale checkpoint, totals unchanged."
  >
    One transaction per batch: derive records, upsert them (`ON CONFLICT` on the
    deterministic key), advance `usage_checkpoints.last_event_id`, commit. Crash
    before commit ⇒ full replay of the batch ⇒ the upserts land on the same rows.
    The deterministic key is the design decision: `(sandbox_id, metric,
    source_generation)` pins a record to the event that opened it.
  </Hint>
  <Hint
    title="Diagnosing the likely failure: totals drift on replay"
    check="hack/validate-17.sh wipes usage_records and the checkpoint, reruns the processor from generation zero, and the per-metric totals match the originals exactly."
  >
    If replay changes totals, the bug is usually one of two: a record key that includes
    something non-deterministic (a timestamp taken at processing time), or an open
    interval that was extended by insert instead of upsert (look for two rows per
    running span). The wipe-and-replay check in the validate script is the pipeline's
    own conformance test — run it after every processor change.
  </Hint>
</HintSteps>

## Definition of done

Unit tests (`make test`):

- `TestRuntimeSecondsFromEvents` — table: clean stop, crash truncation, open
  interval, restart pattern.
- `TestUsageProcessorIsIdempotent` — replay from a stale checkpoint changes no
  totals.
- `TestEventsCarryActorAndReason` — every emission site sets both; unknown reason
  codes fail closed.

Integration (`hack/validate-17.sh`, Lima):

- A driven lifecycle (create, exec, sleep, stop) yields usage records whose runtime
  quantity matches the slept duration within one rounding unit and whose operation
  quantities match the exact call counts.
- Wipe-and-replay: usage_records and checkpoint deleted, processor rerun from
  generation zero, `GET /v1/usage` returns identical totals.

Deliberately untested and deliberately absent: rollups, pricing, and invoices (the
recorded sequel below); payment processing; resource-seconds (CPU-seconds,
GB-seconds) — the usage-snapshot path is recorded as the extension for
when a runtime exposes cgroup stats; periodic metering ticks and explicit
UsageStarted/UsageStopped events — both noted as the resilient-at-scale alternatives
this scale does not need; host-level utilization economics (infrastructure cost vs
revenue), which becomes possible after roadmaps 13–14 but is analysis, not pipeline.

## Solo-developer tradeoffs

Commercial platforms run metering as separate services on a message bus with
periodic-tick events, because at their scale a missed Stopped event is a certainty
and ticks bound the loss; your events are rows in the same Postgres, the processor is
a goroutine, and the checkpoint is a row — the same concepts with the operational
surface of one binary. They also run rating and invoicing above this line; you stop
at measurement, because a rate applied to one tenant's usage teaches nothing the
sequel section does not already describe. The single-process choice is reversible by
design: the package boundary and own-tables rule mean "extract a usage service" is a
deployment change, not a rewrite — which is exactly the claim the package-boundaries
reference makes, tested against a real subsystem.

## Recorded sequel: rollups, pricing, and invoices

Billing machinery is premature for a platform with one tenant, so the three stages
above `usage_records` are recorded here rather than built. They cost nothing to defer:
the wipe-and-replay derivability test — the property that proves the controller stayed
a fact-emitter — already runs at the `usage_records` boundary, so the pipeline's
correctness story is complete without a price attached to anything.

What the sequel would add, in order:

- **`usage_daily(tenant_id, day, metric, quantity)`** — a second idempotent
  derivation, not a trigger: recompute each affected `(tenant, day, metric)` from
  usage_records with `INSERT ... ON CONFLICT DO UPDATE`, full recompute per key rather
  than incremental addition, so replays converge instead of accumulating. Day
  boundaries in UTC, written down, because timezone choice is billing policy. The
  motivation is query shape — "this month's invoice" must not scan every event ever
  written — which is a volume problem this platform does not have yet.
- **A pricing engine as pure configuration.** Everything upstream is measurement; the
  engine itself is multiplication. Keeping it a pure `invoice(rollups, priceList)
  Invoice` means price changes never touch the pipeline, currency rounding lives in
  exactly one place (integer cents, half-up, documented), and the test is a table:
  rollups in, line items out. The temptation to let the processor "just apply the rate
  while it's there" recreates the coupling the whole design argues against — a rate
  change would then rewrite historical usage, and usage is supposed to be a fact.
- **Invoices as documents** (JSON plus rendered text), not payment integrations, from
  a versioned price-list file stamped into each invoice so a regenerated invoice for a
  closed month reproduces byte-identical totals.

The trigger for building it: a second paying tenant, or any moment a number leaves
this system as a charge rather than a measurement.
