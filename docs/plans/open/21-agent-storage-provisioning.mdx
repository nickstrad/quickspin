# 21 — Per-agent persistent storage provisioning

Depends on: 05, 11, 20 (the DSN is delivered on roadmap 20's secret rail).

<Callout tone="note" title="Removed from the active roadmap — optional tail, snapshots first">
  Durable agent state is served first by roadmap 12's snapshots: save/restore preserves
  the filesystem, so installed dependencies, written code, and local SQLite files
  survive a sandbox. Brokering cloud databases is premature until a real consumer
  outgrows that. Revisit this plan when an agent appears whose state must outlive
  snapshots or be shared across sandboxes. One idea is worth carrying forward either
  way: DSN-on-the-secret-rail is the test of whether roadmap 20's `Secret` abstraction
  was right, and a fake provisioner is enough to prove it.
</Callout>

## Summary

Give agents durable state that outlives any sandbox: a `StorageProvisioner` interface
that turns a caller-chosen storage key into a real cloud database, with two
implementations — Turso (SQLite-compatible) and Neon (Postgres) — behind the same
contract, proven equivalent by a shared conformance suite in the style of roadmap 19. The
control plane wires it in: a sandbox create request may name a storage key, the plane
ensures the database exists (idempotently), and the connection string arrives inside
the sandbox as a roadmap 20 secret file. Storage lifecycle is deliberately independent of
sandbox lifecycle — destroying a sandbox never deletes data; deletion is its own
explicit, tenant-scoped API call.

<KeyPoint label="Identity lives with the caller">
  Quickspin sandboxes are ephemeral on purpose, and this roadmap does not add an "agent"
  entity to change that. The durable identity is a caller-supplied opaque key: the
  platform's whole promise is that the same (tenant, key) pair always resolves to the
  same database. What an "agent" is remains the client's business — exactly where the
  agent logic already lives (roadmap 24).
</KeyPoint>

## Industry context

This is the platform-as-broker pattern: Heroku add-ons defined it, Vercel Marketplace
storage (Neon, Upstash) is its current form — the platform provisions a third-party
backing service via that vendor's management API and injects credentials into the
workload's runtime. Sandbox vendors mostly stop at ephemeral disks and snapshots;
pairing compute with brokered storage is what turns "run code" into "run a stateful
agent," and Neon markets database-per-agent as a first-class use case (instant
creation, scale-to-zero pricing makes thousands of small databases viable — Turso's
model is the same bet). The engineering pattern under it all is the twelve-factor
"backing services" rule: the workload receives a DSN and treats the database as an
attached resource, so swapping Turso for Neon — or either for anything else — changes
provisioning, never workload code. Note what this is *not*: roadmap 09's Postgres is the
platform's own control-plane store; this roadmap provisions databases the platform never
reads, owned by tenants and touched only by their workloads.

## Key concepts

- Driving SaaS management APIs from Go: auth headers, pagination, error taxonomies,
  and mapping two very different vendor vocabularies onto one interface.
- Idempotency against someone else's cloud: `Ensure` semantics, deterministic naming
  as the reconciliation key, and the create-then-crash window that turns "create" into
  "create if not exists, then look it up."
- A second rep of the conformance-suite pattern (after roadmap 19): one behavioral
  contract, N implementations plus a fake, one shared proof.
- Quota and scoping composition: the new resource inherits roadmap 11's tenant predicate
  and admission-time quota discipline without new mechanisms.
- Credential handoff: composing this roadmap with roadmap 20 so a DSN — which embeds a
  password — never rides an env var or a log line.

### Concept: two databases with nothing in common but SQL

Roadmap 09's Postgres and this roadmap's Neon databases can even live on the same vendor,
which is exactly why the distinction must be explicit: the control-plane store is
*platform* state (sandbox rows, tenants, leases) that quickspin reads on every
request, while provisioned storage is *tenant* state the platform must never read —
it creates the database, hands over the credential, and forgets. The boundary shows
up concretely in the code: the store from roadmap 09 is a dependency injected into the
plane; provisioned databases appear only as rows *in* that store (ref, provider,
remote name, created-at) plus a secret it explicitly does not retain in plaintext.
Blurring this boundary is how platforms end up with support engineers who can read
customer data.

### Concept: Ensure is an upsert against a cloud you don't control

`Ensure(ref)` must be safe to call any number of times, concurrently, across crashes —
because the plane *will* crash between the vendor's create call and its own commit,
and the caller *will* retry. Two mechanisms make it hold. First, deterministic naming:
the remote database's name is derived from the ref (`qs-<tenant>-<hash-of-key>`), so a
retry can find what a crashed attempt created — the name is the reconciliation key,
the same role labels played for roadmap 15's servers. Second, treat the vendor's
"already exists" conflict as success-with-lookup, not failure: create, and on a 409
(or vendor equivalent) fetch the existing database and proceed. The local row is then
written after the remote resource exists, which means the crash window leaves an
*unrecorded remote database* — found again by name on the next Ensure — rather than a
recorded phantom. Orphans in the other direction (created remotely, key never used
again) are swept by a list-by-prefix audit script, the cost-safety lesson from roadmap 15
applied to databases.

### Concept: the storage key is a namespace decision, not a database decision

The API takes any reasonable string as a key (`agent-42`, `research-bot/prod`), but
vendor names have charset and length limits the key must not inherit — hence the hash
in the remote name, with the human-readable ref kept in the store row. Scoping is the
roadmap 11 rule applied on day one: the ref is always (tenant, key), every store query
carries the tenant predicate, and one tenant's `agent-42` is a different database from
another tenant's `agent-42`. Quota follows the same admission pattern — a
`max_databases` column on tenants, checked in the same transaction that inserts the
storage row, with the same race test shape as `TestQuotaRaceOnlyAdmitsCap`.

### Concept: a DSN is a secret wearing a URL costume

`postgres://user:password@host/db` embeds a credential, so every rule from roadmap 20
applies to the whole string: it is a `Secret` in Go, `[REDACTED]` in logs, absent from
inspect, and it enters the sandbox as `/run/quickspin/secrets/storage_dsn` — never as
an env var, never echoed by the CLI. The composition is the point: this roadmap adds no
new secrecy mechanism, it *reuses* the rail, which is the test of whether roadmap 20's
abstraction was right. Inside the sandbox the workload reads the file and connects;
what the platform stores long-term is a design decision this roadmap makes explicitly:
store the DSN encrypted at rest, or store nothing and re-fetch/rotate credentials from
the vendor on each Ensure — the second is less code and the roadmap's default.

## Design and interfaces

```go
type StorageRef struct {
    TenantID string
    Key      string
}

type StorageInfo struct {
    Ref       StorageRef
    Provider  string // "turso" | "neon" | "fake"
    RemoteName string
    DSN       Secret // populated by Ensure; zero when listed
    CreatedAt time.Time
}

var ErrStorageQuotaExceeded = errors.New("storage quota exceeded")

type StorageProvisioner interface {
    // Ensure is idempotent: same ref, same database, any number of calls.
    Ensure(ctx context.Context, ref StorageRef) (StorageInfo, error)
    // Delete is idempotent: deleting an absent ref is nil.
    Delete(ctx context.Context, ref StorageRef) error
    List(ctx context.Context, tenantID string) ([]StorageInfo, error)
}
```

HTTP surface (all tenant-scoped per roadmap 11):

```text
POST /v1/sandboxes           body gains "storage": {"key": "agent-42"}  (optional)
GET  /v1/storage             list this tenant's provisioned databases
DELETE /v1/storage/{key}     explicit, idempotent; 429 quota on create path
```

Committed decisions:

- Storage lifecycle is independent of sandbox lifecycle; nothing cascades from
  sandbox destroy.
- Remote names are `qs-<tenant>-<short-hash(key)>`; the readable key lives only in
  the store.
- The DSN reaches the workload exclusively as the roadmap 20 secret file
  `storage_dsn`; the platform does not persist plaintext DSNs.
- One region per provider, hardcoded in config; multi-region is out of scope.
- Provider selection is per-request (`"provider": "turso"`) with a configured
  default, mirroring the roadmap 16 pool/provider shape.

### Client surfaces

**CLI.** Extend `quickspin sandbox create` with `--storage-key <key>` and optional
`--storage-provider turso|neon`, sending the nested `storage` request field. Add
`quickspin storage ls` (key, provider, remote name, and creation time; never the DSN)
and idempotent `quickspin storage rm <key>`; surface the create-path quota response as
the typed storage-quota error rather than a generic request failure.

**Web app.** Add an optional storage key and provider selector to the sandbox-create
form, plus a tenant storage view listing the same non-secret fields with an explicit
delete action. The sandbox detail may show that storage is attached, but it must never
render or copy `storage_dsn`; quota validation belongs inline on the create form.

## Hint steps

<HintSteps>
  <Hint
    title="Start from the conformance suite, not an adapter"
    check="The suite passes against the fake under make test, including TestEnsureIsIdempotent and TestEnsureConcurrentSameRefYieldsOne."
  >
    Write the behavioral contract first, the way `runtimetest` does for runtimes: a
    function like `RunProvisionerConformance(t, newProvisioner, cleanup)`. The
    concurrent case matters most — fire N goroutines at `Ensure` for one ref and
    assert exactly one database results. Getting the fake to *fail* this (then fixing
    it) teaches the locking the real adapters will need around create-or-lookup.
  </Hint>
  <Hint
    title="Deterministic naming has vendor constraints"
    check="TestRemoteNameStableAndValid shows the same ref always yields the same name, different refs collide only if the hash does, and names satisfy both vendors' documented length/charset rules."
  >
    A short hash (first 10–12 hex chars of SHA-256 over tenant+key) inside a fixed
    prefix keeps names legal everywhere and makes ownership greppable in vendor
    dashboards. Keep the function pure and table-tested; both adapters and the audit
    script must share it — a second implementation that drifts is how orphan sweeps
    go blind.
  </Hint>
  <Hint
    title="Turso: two credentials, two steps"
    check="Gated by TURSO_API_TOKEN + TURSO_ORG, the conformance suite passes live; the resulting DSN connects from a scratch Go program."
  >
    The *platform* API token (from your account) creates and deletes databases; each
    database then needs its own *auth token* minted via the API for the DSN
    (`libsql://<name>-<org>.turso.io` plus the token). Map their 409/404 responses
    onto Ensure/Delete semantics. Watch the deletion→recreation window: recreating a
    just-deleted name can briefly conflict — the conformance cleanup hook should
    tolerate that with a short retry.
  </Hint>
  <Hint
    title="Neon: decide what one ref maps to, then extract the right connection string"
    check="Gated by NEON_API_KEY, the conformance suite passes live and the DSN uses the pooled endpoint."
  >
    Neon's hierarchy is project → branch → database. Simplest legal mapping: one
    project per ref (their API returns the connection URI on create). One project per
    *tenant* with a branch per key is cheaper at scale but drags in branch-management
    edge cases — pick one, record it as a committed decision, and note the other as
    the road not taken. Prefer the pooled connection string; agent workloads open
    connections carelessly, and serverless Postgres punishes that without pgbouncer in
    front.
  </Hint>
  <Hint
    title="The plane composes existing pieces; the only new logic is ordering"
    check="A create request with storage yields a sandbox whose /run/quickspin/secrets/storage_dsn connects; TestStorageQuotaRaceOnlyAdmitsCap passes; destroy leaves the database reachable on the next create with the same key."
  >
    Order inside the create path: admission (quota, in the same transaction as the
    storage-row insert, roadmap 11's shape) → `Ensure` → put the DSN into the spec's
    secrets → the normal sandbox create. An Ensure failure fails the request cleanly
    — nothing was created yet. Sandbox destroy touches none of this. The 429 body
    reuses roadmap 11's quota error shape with a distinct code.
  </Hint>
  <Hint
    title="Diagnosing the likely failure: databases you pay for and cannot explain"
    check="hack/storage-orphans.sh reports zero orphans after a full conformance run, and correctly reports one after you create a database by hand with the qs- prefix."
  >
    When live tests crash mid-run they strand remote databases — that is the failure
    mode to rehearse, not avoid. The audit script lists vendor databases with the
    `qs-` prefix, lists store rows, and prints both set differences. Plant an orphan
    deliberately to prove the script sees it. If orphans recur in normal operation,
    the bug is in Ensure's crash-window ordering — the row was written before the
    remote resource existed.
  </Hint>
</HintSteps>

## Definition of done

Pure unit tests (in `make test`):

- Conformance suite against the fake: `TestEnsureIsIdempotent`,
  `TestEnsureConcurrentSameRefYieldsOne`, `TestDeleteTwiceIsNil`,
  `TestListSeesOnlyTenant`.
- `TestRemoteNameStableAndValid` — deterministic, both vendors' constraints,
  table-driven.
- `TestEnsureAfterPartialFailure` — the fake injects a crash between remote create
  and local record; the retried Ensure converges to one database.
- `TestStorageQuotaRaceOnlyAdmitsCap` — roadmap 11's race shape for `max_databases`.
- `TestDSNIsRedacted` — the DSN rides the `Secret` type through logs and listings.

Live tests (env-gated, one target per provider):

- The same conformance suite against Turso (`TURSO_API_TOKEN`) and Neon
  (`NEON_API_KEY`), each ending with a connect-and-`SELECT 1` through the returned
  DSN, plus full cleanup.

Scripts:

- `hack/storage-orphans.sh` exits 0 with zero orphans after a clean run and detects a
  planted orphan.

Deliberately untested: data migration between providers, backup/restore, credential
rotation, connection pooling behavior under load, vendor rate limits, and billing —
recorded so they are debts, not surprises.

## Solo-developer tradeoffs

A commercial broker meters usage for billing, rotates credentials automatically,
offers regions and size tiers, and runs the orphan sweep as a reconciler with alerts
rather than a script run by hand. This roadmap keeps the part that generalizes — the
provisioner contract, idempotent Ensure, conformance across vendors, tenant scoping —
and accepts manual sweeps, single region, and fetch-don't-store credentials because
one developer's blast radius is one bill. The deeper simplification to make knowingly:
no "agent" entity. If agents later accumulate more platform state than a DSN, that is
the moment to introduce one, with this roadmap's (tenant, key) refs migrating into it.
