# 22 — Git-capable sandboxes and secret injection

Depends on: 03, 04 (12 is where this pays off; 07 must preserve the contract).

## Summary

Make a sandbox capable of the full coding-agent workflow — clone a repo, branch,
commit, push, open a pull request — and give the platform a typed API for it. The
plan has four deliverables: a dev image with `git` and `gh` baked in, a
`Spec.Secrets` mechanism that injects credentials as files (never environment
variables), a redaction discipline that keeps secret values out of every log and
inspect surface the platform produces, and a `Git` operations layer — typed
`Clone`/`Commit`/`Push`/`CreatePR` methods with typed errors, built entirely on plan
03's `Exec`. The proof is end to end: a script drives a sandbox through the typed
layer to open a real pull request against a throwaway repository.

<KeyPoint label="No new runtime verbs">
  Git operations are processes, and plan 03's `Exec` already runs processes — so the
  `Runtime` interface gains nothing. The typed git API is a *library layered above*
  the runtime: it composes Exec calls, parses git's machine-readable output, and maps
  failures to typed errors. That layering is what lets it survive plan 07 (the layer
  rides wherever exec rides) and become an SDK feature in plan 09 unchanged.
</KeyPoint>

## Industry context

Daytona ships `sandbox.git.clone/add/commit/push` as typed SDK methods; E2B leaves git
to the template image and `commands.run`. Both capabilities rest on the same
substrate — a process runner inside the sandbox — and this plan builds both ends:
the exec-driven flow first (it is the debugging tool for everything above it), then
the Daytona-style typed layer, because typed errors and structured status are what an
agent harness can actually branch on, and they cut LLM token spend (one tool call
instead of a shell round-trip per step). Under the hood Daytona's git API does
exactly what you'll do: run git inside the sandbox and parse its output. On secrets, the industry
is unanimous in a way worth copying: Modal has first-class `Secret` objects attached
to functions, Fly has `fly secrets` kept out of `flyctl` output, Kubernetes mounts
Secrets as tmpfs files, and every one of them treats "secret in an env var" as a
legacy compromise — env vars leak through `docker inspect`, `/proc/<pid>/environ`,
crash dumps, and child processes that log their environment. Files with `0400`
permissions have exactly one reader and one audit trail.

## What you'll learn

- Images as the capability contract: what a sandbox can do is decided at image build
  time, not API design time.
- The create→copy→start window: Docker lets you copy files into a *created but not
  yet started* container, which is the natural moment to place secrets.
- Why secrets ride as files: the enumeration of env-var leak channels, and tmpfs vs
  image-layer placement.
- Redaction as a type-system property: a Go `Secret` type whose formatting methods
  refuse to print the value, so a leak requires deliberate effort rather than one
  careless `%+v`.
- Git credential plumbing: how `git` and `gh` discover credentials
  (`GIT_ASKPASS`, credential helpers, `gh auth login --with-token`) and how to feed
  them from a file without touching the environment.
- Least-privilege tokens: GitHub fine-grained PATs scoped to one repository.
- Wrapping a CLI as an API: git's machine-readable porcelain formats
  (`status --porcelain=v2 -z`, `rev-parse`), exit-code and stderr taxonomies, and
  mapping them onto typed Go errors an agent harness can branch on.

### Concept: git needs no API; it needs an image and a credential

Decompose "the agent can make PRs" and no platform work involves git itself:
`git clone` needs the binary and network egress (plan 03's policy), `git commit` needs
an identity (`git config user.email` — bake a default into the image), `git push`
needs a credential, and `gh pr create` needs the same credential plus the `gh` binary.
Every step is an `Exec` call with an argv — which is also the security posture: the
path/argument discipline from plans 03–04 (argv vectors, never `sh -c`
interpolation) already covers it. The image is therefore a real platform artifact, not
a test fixture: a `Dockerfile` in the repo, a `make image-dev` target, and a pinned
tag the validation script uses. This is E2B's "template" concept at its smallest.
The typed git layer changes none of this — it is the same Exec calls with the shell
round-trips replaced by Go.

### Concept: a typed git API is a parser and an error taxonomy, not new plumbing

The value of `git.Commit(ctx, msg)` over `Exec("git", "commit", ...)` is entirely in
what comes *back*: a SHA instead of stdout to grep, `ErrNothingToCommit` instead of
exit code 1 with prose on stderr. Building it is two disciplines. First, always ask
git for machine-readable output where it offers one — `status --porcelain=v2 -z` is a
documented, stable, NUL-delimited format, `rev-parse HEAD` yields the SHA, `push
--porcelain` reports per-ref results — and never parse the human-facing text, which
varies by version and locale. Second, build the error taxonomy empirically: run each
failure for real (bad token, no upstream, empty index, existing PR), record the exit
code and the stable stderr fragment, and encode that mapping in one table-tested
function per operation. Where git gives no machine format (authentication failures
are prose on stderr), match conservatively and fall back to a generic error carrying
the captured stderr — a typed layer that guesses wrong is worse than one that
admits it doesn't know. `gh` is the easy half: `--json` flags give real JSON for PR
creation and lookup.

### Concept: an environment variable is a broadcast channel

`Spec.Env` exists and would work — that is exactly why this plan needs a rule, not a
shrug. A value placed in a container's environment is readable via `docker inspect`
(any host tool, forever, including after the process exits), `/proc/<pid>/environ`
(any same-user process in the sandbox), and every child process, some of which — CI
tools, crash reporters, verbose test runners — print their environment as a feature.
A file at `/run/quickspin/secrets/<name>` with mode `0400` has none of those
properties: it is not in inspect output, not inherited, and read only by code that
names it explicitly. The delivery mechanism is plan 04's own machinery pointed at a
new moment in the lifecycle: Docker's copy API accepts a **created, not yet started**
container, so `Create` can place secret files before the workload's first instruction
runs — no race where the process starts secretless, no secrets in the image layer,
no re-use of `Spec.Env`.

### Concept: redaction is a property of the type, not the caller's discipline

The platform already logs structured records (plan "structured runtime and CLI
logging"), and a secret will eventually flow near a log call — the only question is
whether the logger can betray it. Storing secret values as `string` means one
`slog.Any("spec", spec)` or one `%+v` in an error path prints the token. The fix is a
`Secret` type holding the value unexported, whose `String()`, `GoString()`,
`MarshalText/JSON`, and `LogValue()` all return `[REDACTED]` — so the *default*
behavior of every formatting and logging path is safe, and reaching the value requires
calling an explicit `Reveal()` (or similar) that is easy to grep for in review. This
inverts the usual failure mode: instead of every log site needing care, only the
handful of `Reveal` sites do.

<Callout tone="warning" title="Redact the derived strings too">
  The token also appears inside things built from it — a clone URL with an embedded
  credential, a `gh auth` command line, an error message quoting a failed request.
  Prefer constructions that never embed the secret (credential helpers over
  `https://token@host` URLs), and treat any `Reveal()` result as radioactive: it goes
  into a file or a process's stdin, never into an argv (visible in `ps`) or an error.
</Callout>

### Concept: the credential's scope is the blast radius

A sandbox runs untrusted (or at least unreviewed, LLM-written) code next to a token
that can write to your repositories. The token *will* be readable by the workload —
that is its purpose — so containment comes from scope, not hiding: a GitHub
fine-grained personal access token restricted to the one target repository, with
`contents:write` and `pull_requests:write` only, expiring in days. The threat-model
discipline from plan 08 applies verbatim: write down that a malicious workload can
push garbage branches and open garbage PRs on that one repo, and that this is
accepted; it cannot touch other repos, org settings, or the platform itself.

## Design and interfaces

```go
type Secret struct {
    // unexported value; constructed via NewSecret(string)
}

func (s Secret) String() string       // "[REDACTED]"
func (s Secret) LogValue() slog.Value // "[REDACTED]"
func (s Secret) Reveal() string       // the only accessor

type Spec struct {
    Image   string
    Env     map[string]string
    Secrets map[string]Secret // written to /run/quickspin/secrets/<name>, mode 0400
}
```

The git layer (new package, e.g. `internal/gitops`, built only on `Runtime.Exec`):

```go
type Git struct {
    // bound to a runtime, sandbox ID, and working directory at construction
}

type GitStatus struct {
    Branch string
    Ahead  int
    Behind int
    Dirty  []string // paths with uncommitted changes
}

type PROptions struct {
    Title string
    Body  string
    Base  string
}

var (
    ErrGitAuth         = errors.New("git authentication failed")
    ErrNotARepo        = errors.New("not a git repository")
    ErrNothingToCommit = errors.New("nothing to commit")
    ErrPRExists        = errors.New("pull request already exists for branch")
)

func (g *Git) Clone(ctx context.Context, url, dir string) error
func (g *Git) Checkout(ctx context.Context, branch string, create bool) error
func (g *Git) Status(ctx context.Context) (GitStatus, error)
func (g *Git) Add(ctx context.Context, paths ...string) error
func (g *Git) Commit(ctx context.Context, message string) (sha string, err error)
func (g *Git) Push(ctx context.Context) error
func (g *Git) CreatePR(ctx context.Context, opts PROptions) (url string, err error)
```

Committed decisions:

- Secret file names are validated like plan 04 paths (single path element, no
  separators or dot-segments); the directory is fixed at `/run/quickspin/secrets`.
- Secrets never appear in container env, image layers, `docker inspect` output, logs,
  or CLI output. `Spec.Env` remains for non-secret configuration.
- The `Runtime` interface is unchanged: the git layer lives above it, driving `Exec`
  with argv vectors. Exposing it over HTTP and in the SDK is deferred to plans 07/09,
  which inherit this package's types as their contract.
- Output parsing uses only machine-readable git formats (`--porcelain=v2 -z`,
  `rev-parse`, `push --porcelain`, `gh --json`); typed errors come from a per-operation
  exit-code/stderr mapping, with a generic stderr-carrying error as the honest
  fallback.
- The dev image lives in the repo (`images/dev/Dockerfile`, `make image-dev`), pins
  tool versions, and sets a default git identity.
- CLI: `quickspin sandbox create --secret NAME=@file` reads values from files, never
  from the command line itself (argv is visible in `ps` and shell history).

<HintSteps>
  <Hint
    title="Start with the Secret type — it has no dependencies"
    check="TestSecretRedactsEverywhere passes under make test, covering %s, %v, %+v, %#v, fmt.Sprint, json.Marshal, and slog output."
  >
    A struct with one unexported string field. Implement `fmt.Stringer`,
    `fmt.GoStringer`, `encoding.TextMarshaler`, `json.Marshaler`, and `slog.LogValuer`
    — that set covers every path the standard library uses to turn a value into text.
    Write the test first by trying to leak it every way you can think of; each failing
    leak names the next interface to implement.
  </Hint>
  <Hint
    title="The dev image is ordinary Docker, but pin what the tests will assert"
    check="make image-dev builds; exec of `git --version` and `gh --version` in a sandbox from the image succeeds."
  >
    Base it on something small (`debian:bookworm-slim` or `alpine` — note `gh`
    installation differs per base). Set `git config --system user.email/user.name` in
    the Dockerfile so commits work before any per-sandbox setup, and keep a long-running
    default command per plan 02's pattern. Remember the image must exist inside the
    test VM's daemon, not your host's.
  </Hint>
  <Hint
    title="Secrets land between create and start"
    check="A created sandbox with one secret shows the file with mode 0400 and exact content via exec cat/stat, and docker inspect of the container shows no trace of the value."
  >
    Docker's `CopyToContainer` works on a created container — reorder `Create` so the
    copy happens after `ContainerCreate` and before `ContainerStart`. Build the archive
    with the plan 04 helpers: a directory header for `/run/quickspin/secrets` (mode
    0700), then one entry per secret. If the copy fails, destroy the created container
    rather than leaking it half-configured — this is the same clean-up-on-partial-failure
    lesson as plan 02's create path.
  </Hint>
  <Hint
    title="Feed gh and git from the file, never the environment or argv"
    check="Inside the sandbox, `gh auth status` reports a logged-in token whose value appears in no ps output, no env, and no shell history."
  >
    `gh auth login --with-token` reads the token from stdin — so the in-sandbox step
    is `sh -c 'gh auth login --with-token < /run/quickspin/secrets/github_token'`
    (here `sh -c` is fine: the *path* is fixed and validated; it is the secret value
    that must not appear in the command). `gh auth setup-git` then registers gh as
    git's credential helper, covering `git push` too. Avoid
    `https://x:TOKEN@github.com` remote URLs — the token would land in
    `.git/config`.
  </Hint>
  <Hint
    title="The typed layer starts as pure parsers, not as methods"
    check="TestParseStatusPorcelainV2 and TestMapCommitError pass under make test with no Docker, covering clean, dirty, ahead/behind, detached HEAD, and each typed error's exit-code/stderr row."
  >
    Write `parseStatusV2([]byte) (GitStatus, error)` and the per-operation error
    mappers as pure functions first — feed them captured real output (run the failure
    cases by hand in a sandbox and paste the bytes into the test table). Only then
    wrap them in `Git` methods that call `Exec` and delegate. The porcelain v2 format
    is documented under `git-status`; use `-z` so filenames with spaces don't fork
    your parser. For `CreatePR`, `gh pr create` prints the URL on stdout and
    `gh pr view --json url` confirms it; an existing PR surfaces as a non-zero exit
    with a stable "already exists" fragment — that's `ErrPRExists`.
  </Hint>
  <Hint
    title="The validation script is gated and self-cleaning"
    check="hack/validate-22.sh exits 0, prints the PR URL, and a final grep of all captured logs and inspect output for the raw token finds nothing; without QS_TEST_REPO it skips cleanly."
  >
    Gate on `GITHUB_TOKEN` and `QS_TEST_REPO` env vars (the throwaway repo you make by
    hand once). The script: create sandbox with the secret → exec the auth, clone,
    branch, commit, push, `gh pr create` sequence → capture the PR URL → close the PR
    and delete the branch via `gh` → destroy the sandbox. Save every byte of output
    the run produced (CLI stdout/stderr, structured logs, `docker inspect`) into a
    temp dir and end with the negative grep — the grep is the test.
  </Hint>
  <Hint
    title="Diagnosing the likely failure: the token leaked somewhere"
    check="You can name the exact surface a planted fake secret appears on, and after the fix the plant is undetectable."
  >
    Debug with a plant: create a sandbox with a distinctive fake secret
    (`LEAKCANARY123`) and grep for it across `docker inspect`, the daemon log, your
    structured logs at debug level, `ps auxe` inside the sandbox, and
    `/proc/1/environ`. The usual culprits: an error message that embeds the value
    (wrap errors with the secret's *name*, never its content), a debug log of the full
    `Spec`, or a helper that flattened `Secrets` into env for convenience. Fix the
    type or the boundary, not the individual call site.
  </Hint>
</HintSteps>

## Definition of done

Pure unit tests (in `make test`):

- `TestSecretRedactsEverywhere` — `%s`, `%v`, `%+v`, `%#v`, `fmt.Sprint`,
  `json.Marshal`, and `slog` output of a `Secret` and of a `Spec` containing one all
  yield `[REDACTED]`, never the value.
- `TestSecretNameValidation` — names with `/`, `..`, empty, or absolute forms are
  rejected before any Docker call.
- `TestParseStatusPorcelainV2` — table-driven over captured real output: clean,
  dirty, renamed, ahead/behind, detached HEAD.
- `TestMapGitErrors` — each typed error's exit-code/stderr row maps correctly, and
  unknown failures fall back to a stderr-carrying generic error.

Integration tests (`make test-docker`):

- `TestSecretFileModeAndContent` — the file exists at the committed path with mode
  `0400` and byte-exact content.
- `TestSecretAbsentFromInspect` — the container's inspect output (env, cmd, labels)
  does not contain the value.
- `TestCreateWithSecretCopyFailureCleansUp` — a forced copy failure leaves no
  container behind.
- `TestGitLocalRoundTrip` — against a `file://` bare repo created inside the sandbox
  (no network, no token): `Clone`, `Checkout`, `Add`, `Commit` returns a real SHA,
  `Push`, and `Status` reports clean; `Commit` on a clean tree yields
  `ErrNothingToCommit`.

Validation script:

- `hack/validate-22.sh` — the full clone→branch→commit→push→PR flow through the typed
  git layer against a real throwaway repo, gated on `GITHUB_TOKEN`/`QS_TEST_REPO`,
  ending with a negative grep for the token across all captured output; exits 0 only
  when `CreatePR` returned a URL and the grep found nothing. `ErrGitAuth` and
  `ErrPRExists` are exercised here too (bad token, second PR attempt) since they need
  a real remote.

Deliberately untested: token rotation and revocation, secrets updates on a running
sandbox, symlink games inside the secrets directory, the plan 07 guest-agent transport
of secrets (recorded here as a requirement 07 must preserve: secrets must not transit
in URLs or logs when file serving moves into the guest).

## Solo-developer tradeoffs

Commercial platforms back this with a secrets manager (Modal Secrets, Fly's vault,
cloud KMS), rotation, per-secret audit logs, and OIDC exchange so workloads get
short-lived tokens minted per run instead of a stored PAT. For one developer, a
fine-grained PAT scoped to one repo with a short expiry delivers most of the
containment at none of the infrastructure cost — the deliberate debts are rotation
(you re-mint by hand) and audit (GitHub's token log is the audit). The typed git
layer is deliberately narrower than Daytona's (no pull/fetch/branch-list/diff, one
forge): the seven operations above are what a PR-making agent loop actually calls,
and each additional verb is mostly another parser table — add them when a real
harness (plan 12) asks.
