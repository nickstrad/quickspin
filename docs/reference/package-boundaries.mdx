# Package Boundaries & Dependency Direction

Rules for where new code goes and which package may import which, so that future changes
— new runtime backends, new stores, new transport surfaces — land in the right place
without re-deriving the layout each time. The package names below now match the code;
the rules are meant to outlive any particular snapshot of it.

One rule carries most of the weight:

**Dependencies point from plumbing toward the domain, never back.** Contracts never
import implementations, implementations import only their own contract, and transport
sits on top where nothing but `main` imports it. A change that needs a new import edge
in the other direction is in the wrong package.

---

## The dependency direction

The intended import graph, from sink to surface (arrows = imports):

```
runtime                          the leaf: sandbox execution contract + its types
sandbox        ──► runtime       domain: records, state machine, spec resolution
events         ──► sandbox       domain: the append-only transition log
store          ──► sandbox, events   persistence contract
store/sqlite   ──► store         a store implementation
runtime/docker ──► runtime       a runtime implementation
api            ──► sandbox, runtime      wire DTOs + converters
control        ──► store, sandbox        admission: client intent + policy
reconciler     ──► store, runtime, sandbox   convergence: repairs drift on a ticker
httpapi        ──► control, api, store, runtime   HTTP transport (+ pass-through reads)
client         ──► api, sandbox, runtime     HTTP client
cli            ──► client, daemon        cobra surface
daemon         ──► httpapi, reconciler, store/sqlite, runtime/docker   composition root
cmd/*          ──► cli           thin mains
```

(`errs`, the shared error envelope, is omitted above: it imports nothing from
`internal/` and may be imported from anywhere — see the closing note on tolerated
duplication.)

`events` sits beside `sandbox` rather than inside it: an event is a record of what
happened, not a rule about what a sandbox is, and the state machine must not grow a
dependency on its own audit trail. It is a leaf like `sandbox` — no logging, no SQL, no
wire tags beyond the ones the domain records already carry. The event log is part of the
store contract rather than one implementation's extra, because a transition and its
event have to commit together: `UpdateSandboxState` takes the reason and appends the row,
so no store can offer transitions without history.

`control` and `reconciler` split the store's writers by *source of truth*, not by
call path: control admits client intent (the states `pending` and `stopping`, lease
renewals) after its policy decisions — validation ordering, idempotency rulings, TTL
clamps, error taxonomy — while the reconciler is the only component that transitions
state from runtime facts. Neither is a chokepoint for the other; what keeps two
writers safe is that every write restates the state it read in its WHERE clause, so
the store referees mechanics (guards, event atomicity, idempotent replay) without
learning policy. This split is convention enforced in review, not by the compiler.

Stated as rules rather than a snapshot:

| Rule | Meaning | Example violation |
| --- | --- | --- |
| **Contracts never import implementations** | `runtime` must not import `runtime/docker`; `store` must not import `store/sqlite`. | The `Runtime` interface growing a Docker-shaped parameter. |
| **Implementations import only their contract (and below)** | `store/sqlite` sees `store` and `sandbox`; it never sees `httpapi`, `control`, or a sibling implementation. | A store impl reaching into `api` for a response shape. |
| **Domain stays transport-free** | `sandbox` knows nothing of HTTP, JSON wire shapes, SQL, or cobra. Wire tags live in `api`; column mapping lives in the store impl. | Adding an `http.StatusX` decision to the state machine. |
| **Transport is imported by nothing but `cmd/`** | Nothing depends on `httpapi` or `cli` except the binaries that run them. The client talks to `api`, not the server package. | A test helper in `store` importing `httpapi` for a fixture. |
| **No sibling edges between implementations** | Backends and stores are peers behind their contracts; sharing code between two of them means the shared piece belongs in the contract package. | `runtime/firecracker` importing a helper from `runtime/docker`. |

The graph is easy to check when it matters: `go list -deps ./internal/...` (or a quick
`grep` of imports) answers whether a proposed edge exists, and review should treat a new
back-edge the way it treats a failing test.

## The pluggable-seam triple

Every seam that expects more than one implementation takes the same three-part shape:

1. **A contract package** — the interface, the domain types it speaks, its sentinel
   errors, and the limits that are part of the promise (`runtime.MaxFileSize` is the
   contract's cap, not Docker's).
2. **One subpackage per implementation** — `runtime/docker` today; `runtime/firecracker`
   (roadmap 14), `runtime/kata` (21), `runtime/mini` (13); `store/sqlite` today,
   `store/postgres` (15). The constructor is `New` — `docker.New(...)`, `sqlite.New(...)`
   — because the package name already says which one it is.
3. **A conformance suite in a `*test` subpackage of the contract** — `runtimetest`,
   `storetest`. Every implementation runs the same suite; that suite, not the interface
   alone, is what makes "second backend behind the same API" an honest claim. The testing
   half of this pattern is specified in
   [`runtime-backend-testing.mdx`](runtime-backend-testing.mdx); this document only fixes
   where the pieces live.

The roadmap reuses this triple beyond runtimes and stores: compute providers (roadmap
20, shared provider conformance suite) and storage provisioners (roadmap 23, Turso/Neon
adapters behind one interface) should land in the same shape rather than inventing a
new one.

## Where does new code go

The package-layout projection of
[`code-structure-and-testing.mdx`](code-structure-and-testing.mdx)'s three kinds of
code — that document says how to split and test logic; this table says which package
receives each kind:

| You are writing… | It goes in… | Signal you picked wrong |
| --- | --- | --- |
| A rule about what a sandbox *is* — a legal state transition, a spec default, a validation | `sandbox` | The function needs an HTTP status, a SQL row, or a Docker type to compile. |
| A fact about something that already happened — a lifecycle transition, its reason | `events` | The function recomputes the record from current state instead of reading what was appended. |
| An admission decision on a client request — validation ordering, an idempotency ruling, a TTL clamp, which failures are the client's fault | `control` | It is a one-line pass-through to the store; leave those in the handler. |
| Repair of drift between recorded and observed state — a converge action, a compensation for a write that lost its guard | `reconciler` | It runs during a request instead of a pass; request paths record intent, they do not converge. |
| A request/response shape or its converter | `api` | Only the server or only the client can use it. Wire shapes are shared or they are not wire shapes. |
| Talk to Docker, SQL, tar, or the moby SDK | The implementation subpackage | The contract package needs a new import to accommodate it. |
| An HTTP route, decoding, error-to-status mapping | `httpapi` | Business decisions creep in; extract them down into `control` or `sandbox`. |
| A cobra command, flag, or table renderer | `cli` | It constructs a runtime or store; composition belongs behind the serve entry point, not in the command tree. |

Two deliberate asymmetries worth keeping:

- **Interfaces live where they are consumed, types live with their interface.**
  `runtime.Spec` stays in `runtime` because it parameterizes the `Runtime` interface —
  a neutral `types` package that exists only to be neutral is a grab bag with better
  branding.
- **`control` covers only operations that decide something.** List/inspect/read are
  pass-throughs and stay that way. A service layer that wraps every store call adds a
  file to every change and information to none.

## Anti-patterns to refuse in review

- **Layer-cake packages** — `models/`, `services/`, `handlers/`, `domain/`. Packages are
  named for what they are about (`sandbox`, `runtime`, `store`), not for which layer of
  a diagram they occupy.
- **Grab bags** — `util/`, `common/`, `helpers/`. A package everything depends on is a
  package nothing can change; the narrow exception is a true leaf like `errs`, which
  earns broad import by importing nothing itself (see below).
- **Wrap-everything service layers** — see above; the layer earns its place per
  operation, not per package.
- **Convenience back-edges** — importing the server package for one struct, importing a
  sibling backend for one helper. The one struct moves to `api`; the one helper moves to
  the contract package or gets copied.

And the positive form of the last point: **tolerated duplication is a choice, not an
oversight.** A little copying is better than a little dependency; the review question is
whether the duplication is stable, not whether it exists — and whether the shared thing
would be a leaf. The per-package `errors.go` files
([`error-handling-and-logging.mdx`](error-handling-and-logging.mdx)) were copied until the
envelope stopped changing, then collapsed onto `internal/errs`, which imports nothing from
`internal/` and so cannot become an everything-dependency.
