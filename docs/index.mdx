# Documentation index

The human-facing reader indexes only the platform roadmaps in `plans/open/` and
`plans/closed/`. This index, [`reader-guide.mdx`](reader-guide.mdx),
[`plans/AGENTS.md`](plans/AGENTS.md), and [`reference/`](reference/) are supporting
material for agents that author or update those roadmaps.

## Roadmaps

The roadmap outlines Quickspin's intended future state as a sequence of independently
verifiable platform milestones. It complements the codebase; it does not describe current
behavior or authorize implementation by itself.

- [`plans/open/`](plans/open/) contains future or in-progress milestones.
- [`plans/closed/`](plans/closed/) preserves delivered milestones as historical context.
- [`plans/AGENTS.md`](plans/AGENTS.md) defines the required structure for every roadmap,
  including the verifiable definition-of-done requirement.

### Platform roadmap

Milestones 01–06 are complete. Roadmaps 07–25 describe intended future states rather
than current behavior; the codebase remains authoritative.

The ordering is platform-first: 01–08 are the sequential spine ending in the
three-binary architecture (control plane, host agent, guest agent); 09–16 are the
production track that takes it to live, multi-host, metered cloud operation — auth,
snapshots, Postgres, a manually-accepted prod deployment, host registration and
placement, provisioning and observability, compute pools, and usage metering; 17–19
add compute backends in order of least invasiveness (Firecracker behind the existing
seams, cloud-VM providers for it, then Kubernetes + Kata); 20–21 are the
agent-workflow rails (PR-capable sandboxes with secret injection, brokered per-agent
storage); 22–24 are the deliberately-last SDK-and-demo tail — TypeScript and Python
SDKs, then the agent-harness capstone driving the finished platform; 25 is an
optional isolation deep dive that can slot in any time after 01.

   VM, Docker socket, Go cross-compilation, environment validation script.
2. [`02-sandbox-runtime-lifecycle.mdx`](plans/closed/02-sandbox-runtime-lifecycle.mdx) —

6. [`06-reconciler-leases-events.mdx`](plans/closed/06-reconciler-leases-events.mdx) —

9. [`09-auth-tenancy-quotas.mdx`](plans/open/09-auth-tenancy-quotas.mdx) — API keys,

11. [`11-postgres-store.mdx`](plans/open/11-postgres-store.mdx) — pluggable store:

12. [`12-prod-single-host.mdx`](plans/open/12-prod-single-host.mdx) — first live

13. [`13-host-registration-placement.mdx`](plans/open/13-host-registration-placement.mdx)
    — host registration, heartbeats, capacity-aware placement, dead-host handling;

14. [`14-host-provisioning-observability.mdx`](plans/open/14-host-provisioning-observability.mdx)

15. [`15-compute-pools-capacity-admin.mdx`](plans/open/15-compute-pools-capacity-admin.mdx)
    — compute pools as first-class data, the provider registry, `quickspin admin
    pool` scale/adopt verbs, pool-aware placement.
16. [`16-events-usage-metering.mdx`](plans/open/16-events-usage-metering.mdx) — event
    enrichment (actor, reason codes, tenant) and the metering pipeline: events →
    usage processor → usage records → rollups → pricing → invoices.
17. [`17-firecracker-backend.mdx`](plans/open/17-firecracker-backend.mdx) — deep dive:
    Firecracker microVM as a second `Runtime` backend behind the same API, ending
    with the prod cutover from Docker.
18. [`18-ec2-digitalocean-providers.mdx`](plans/open/18-ec2-digitalocean-providers.mdx)
    — EC2 and DigitalOcean provider adapters for Firecracker pools, a shared
    provider conformance suite, the `/dev/kvm` preflight.
19. [`19-kubernetes-kata-backend.mdx`](plans/open/19-kubernetes-kata-backend.mdx) —
    deep dive: Kata Containers pods on Kubernetes as a third `Runtime` backend,

20. [`20-git-capable-sandboxes-secrets.mdx`](plans/open/20-git-capable-sandboxes-secrets.mdx)
    — dev image with git/gh, file-based secret injection with redaction, and a typed
    git operations layer (clone/commit/push/PR) over `Exec`.
21. [`21-agent-storage-provisioning.mdx`](plans/open/21-agent-storage-provisioning.mdx)
    — per-agent persistent databases behind a `StorageProvisioner` interface: Turso

22. [`22-typescript-sdk.mdx`](plans/open/22-typescript-sdk.mdx) — generated TypeScript

23. [`23-python-sdk.mdx`](plans/open/23-python-sdk.mdx) — generated Python SDK; API
    symmetry check across languages.
24. [`24-agent-harness-demo.mdx`](plans/open/24-agent-harness-demo.mdx) — capstone:
    external repo imports the SDK and an LLM agent develops code in a sandbox.
25. [`25-mini-container-runtime.mdx`](plans/open/25-mini-container-runtime.mdx) —
    optional deep dive: namespaces, pivot_root, cgroups, capabilities by hand.

Ordering: the spine is 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 and must be sequential
(each extends the same interfaces; 08 completes the three-binary architecture). The
production track 09 → 10 → 11 → 12 → 13 → 14 → 15 → 16 is the platform-first core:
09–11 finish the store and tenancy shape, 12 is the manually-accepted single-host
prod launch, 13–14 grow it to a monitored multi-host fleet, 15 makes capacity
first-class, and 16 adds metering on the enriched event log. The compute track
17 → &#123;18, 19&#125; follows in least-invasive order: 17 slides Firecracker behind
the roadmap 08 seams and cuts prod over; 18 needs 15 and 17; 19's runtime-backend
half (tasks 1–4) needs only 07 and can run in parallel, while its pool integration
needs 15. The agent-workflow rails come next: 20 needs only 03 and 04 but sits here
so its secret rail and git layer are in place just before the SDKs expose them; 21
needs 05, 09, and 20. The deliberately-last tail is 22 → 23 → 24: SDKs generated
against the finished platform contract, then the agent-harness capstone as the first
external consumer — sequenced last so coding workloads only arrive after prod has
been accepted by hand. 25 is independent of everything after 01 and can slot anywhere
as a change of pace. Each roadmap's `Depends on:` header is authoritative where this
summary is coarse.

## Reference

[`reference/`](reference/) contains forward-looking technical notes, architectural options,
and technical background. Reference documents are not specifications for current code.

Current reference documents:

- [`reference/error-handling-and-logging.mdx`](reference/error-handling-and-logging.mdx)
  proposes per-package error types (`E` at the boundary / `Wrap` above it), one log per
  error, and `slog` child loggers threaded through constructors.
- [`reference/code-structure-and-testing.mdx`](reference/code-structure-and-testing.mdx)
  proposes separating decisions from Docker/HTTP plumbing, when to extract a pure
  function, what to test at each layer, and which comments earn their place.
- [`reference/runtime-backend-testing.mdx`](reference/runtime-backend-testing.mdx)
  defines the reusable test layers, core runtime conformance contract, live harness
  responsibilities, and the checklist every later runtime roadmap should extend.
- [`reference/docker-test-architecture-explained.mdx`](reference/docker-test-architecture-explained.mdx)
  is the concept-first companion to the rulebook above: it explains the implemented
  test lanes — table tests, the fake daemon, `runtimetest.Fake`, conformance, and the
  Lima live harness — with diagrams, the reasoning behind each decision, and how the
  shape extends to future runtimes.
- [`reference/package-boundaries.mdx`](reference/package-boundaries.mdx) proposes the
  package layout rules: dependency direction, the contract / implementation /
  conformance-suite triple for pluggable seams, where new code goes, and the
  anti-patterns to refuse in review.
- [`reference/concurrency-and-state.mdx`](reference/concurrency-and-state.mdx) proposes how
  the future control plane and workers should guard shared state around slow Docker I/O —
  the four helper categories, the upsert pattern for read-modify-write with I/O between,
  and how to race-test them.

These references describe conventions to adopt, not current behavior. They are intended
as a lens for a second pass over the roadmaps.
