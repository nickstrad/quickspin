# Documentation

This directory contains Quickspin's plans and reference material. The codebase describes
what exists today; documents may also discuss work that has not been implemented.

Run `make docs` from the repository root to open the local MDX reader. The reader provides
search, plan navigation, per-document outlines, code highlighting, and reusable study
components. See the [`reader guide`](reader-guide.mdx) for the available MDX components.

## Running the tests

Scope the run to the package you are working in — it is fast enough to sit in a tight
loop, and it stays green while other packages are mid-change:

```sh
go test ./internal/runtime/            # one package
go test ./internal/runtime/ -v         # per-test names, including subtests
go test ./internal/runtime/ -run TestEnvToArgs -v      # one test
go test ./internal/runtime/ -run 'TestEnvToArgs/sorted' # one subtest
```

`-run` takes a regular expression, and a slash descends into `t.Run` subtests — so a
table-driven test can be narrowed to the single row you are fixing.

### Just the names of what failed

Once a table-driven suite has a few hundred rows, the failure detail is longer than the
screen. This prints one failing test per line and nothing else:

```sh
go test ./internal/runtime/ 2>&1 | sed -n 's/^ *--- FAIL: \([^ ]*\).*/\1/p'
```

No `-v` — `go test` already prints `--- FAIL:` lines for failures only, so adding `-v`
would bury them under every passing test. If `jq` is installed, the structured form does
the same job without pattern-matching human-readable output:

```sh
go test -json ./internal/runtime/ | jq -r 'select(.Action == "fail") | .Test // empty'
```

Both list a parent test alongside its failing subtests (`TestEnvToArgs` and
`TestEnvToArgs/single_pair`), because a parent fails when any row under it does. That is
the tree, not duplication — the parent name is what you feed back to `-run` to work the
whole group.

<Callout tone="note" title="A passing test that is not re-run">
  Go caches successful results and prints `(cached)` instead of running them again. The
  cache keys on the test binary and its inputs, so editing Go code invalidates it — but
  a test whose outcome depends on something Go cannot see, like the Docker daemon's
  state, can go stale. Add `-count=1` to force a real run.
</Callout>

Repository-wide commands, all from the root:

| Command | What it does |
| --- | --- |
| `make test` | every Go test in the module; needs no Docker |
| `make test-docker` | the live Docker suite and CLI smoke against the dedicated test VM |
| `make test-docker-clean` | removes managed containers a failed live run left behind |
| `make test-docker-setup` | creates the dedicated test VM without running a test |
| `make test-docker-teardown` | deletes the dedicated test VM |
| `make fmt` | gofmt; must leave nothing to change |
| `make vet` | `go vet`; must be clean before a change is done |
| `make build` | builds the CLI into `bin/` |
| `make docs` | starts this reader |
| `make docs-build` | type-checks and produces a static docs build |

<Callout tone="idea" title="A watch loop, if you want one">
  Go has no built-in file watcher. `brew install entr`, then:

  ```sh
  ls internal/runtime/*.go | entr -c go test ./internal/runtime/
  ```

  `-c` clears the screen between runs, so what you see is always the current result
  rather than a scrollback of old ones. Re-run the `ls` when you add a file — `entr`
  watches the list it was given, not the directory.
</Callout>

There are two suites. Daemon-free tests — pure helpers, the Docker adapter against an
`httptest.Server`, and consumers driven by `runtimetest.Fake` — stay in `make test`, which
works on a machine with no Docker at all and reports the live suite as skipped. Tests that
need a real daemon run under `make test-docker`, which owns a dedicated
`quickspin-runtime-test` Lima VM, passes its forwarded socket as `DOCKER_HOST`, and never
touches your active Docker context or the development `quickspin` VM. Keeping them apart
is what lets the fast loop above stay fast.

`make test-docker` refuses to start if that VM already holds Quickspin containers: on a
daemon only tests use, leftovers can only mean a previous run leaked, and cleaning them
silently would erase the signal. `make test-docker-clean` is the explicit remedy. The
rules behind both suites live in
[`reference/runtime-backend-testing.mdx`](reference/runtime-backend-testing.mdx).

`make test-docker` needs `limactl`, `docker`, `go`, and `jq`.

## Plans

Plans describe bounded implementation work. Moving a plan records its lifecycle; it does
not by itself authorize implementation.

- [`plans/open/`](plans/open/) contains proposed plans and work that is still in progress.
- [`plans/closed/`](plans/closed/) contains completed plans preserved for historical
  context.
- [`plans/AGENTS.md`](plans/AGENTS.md) defines the required structure for every plan,
  including the verifiable definition-of-done requirement.

### One-off implementation work

[`Docker runtime test foundation`](docker-runtime-testing-plan.mdx) is an unnumbered,
bounded coding plan for daemon-free Docker adapter coverage, shared runtime conformance,
live tests through a dedicated reusable Lima VM, and one compiled-CLI lifecycle smoke
(a fresh disposable-VM lane is deferred until CI exists).
It is intentionally outside the platform learning sequence: implementing it strengthens
the test seam used by later runtime plans without adding a new platform capability.

### The platform learning path (open)

Plans 01–12 build the platform incrementally; 13–14 are isolation deep dives that can
run in parallel after their stated dependencies; 15–18 are the production track that
takes the platform to live cloud hosts; 19–21 are the compute track that makes
capacity a first-class subsystem — pools and the capacity admin surface, then one
plan per new compute approach (Firecracker on cloud VMs; Kubernetes + Kata); 22–23
are the agent-workflow track that turns the platform toward its coding-agent
customers — PR-capable sandboxes with secret injection, then brokered per-agent
persistent storage.

1. [`01-linux-lab-environment.mdx`](plans/open/01-linux-lab-environment.mdx) — Lima Linux
   VM, Docker socket, Go cross-compilation, environment validation script.
2. [`02-sandbox-runtime-lifecycle.mdx`](plans/open/02-sandbox-runtime-lifecycle.mdx) —

    Firecracker microVM as a second `Runtime` backend behind the same API.

Ordering: the spine is 01 → 02 → 03 → 04 → 05 → 06 → 07 and must be sequential (each
extends the same interfaces). After 07, work can proceed in parallel batches: &#123;08&#125;
alongside finishing touches on 07; then &#123;09 → 10, 11, 14, 15&#125; are mutually independent
(15 needs 08; 14 and 11 need only 07); 12 needs 09 and 11; 13 is independent of
everything after 01 and can be slotted anywhere as a change of pace. The production
tail 16 → 17 → 18 is sequential and needs 12, 14, and 15 complete. The compute track
is 19 → &#123;20, 21&#125;: 19 needs 17 and 18, then 20 and 21 are mutually independent —
and 21's runtime-backend half (tasks 1–4) needs only 07, so it can run in parallel
with 14–18 as a second deep dive before its pool integration lands. The
agent-workflow track: 22 needs only 03 and 04, so it can slot in any time after the
spine's filesystem work (12 is where it pays off, and 07/09 later expose its git
layer); 23 needs 05, 08, and 22. Each plan's `Depends on:` header is authoritative
where this summary is coarse.

These references describe conventions to adopt, not current behavior. They are intended
as a lens for a second pass over the plans.
